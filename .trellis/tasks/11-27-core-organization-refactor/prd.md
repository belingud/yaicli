# 代码组织渐进式重构

## Goal

在保持 YAICLI 轻量、通用、可自定义定位及现有行为的前提下，明确核心模块的职责和依赖，使新增命令、维护工具执行、处理会话状态时不必同时修改大型协调模块。

用户于 2026-11-27 批准补测优先及命令/工具并行的更新方案，开始第一阶段。父任务负责需求、阶段边界及最终集成验收，实际实现由三个子任务按顺序完成。

## Requirements

### R1：统一命令定义及工具入口

命令的处理函数、别名、帮助、补全及参数接收规则有一份权威定义；工具声明、筛选、权限评估、执行和展示分工清楚，保留现有入口及自定义工具加载契约。

负责子任务：../11-27-command-tool-boundaries/。

### R2：明确 CLI 与计划模块的职责

CLI 保留应用组装和交互循环；会话操作、机器输出和计划协调有清晰入口。命令处理通过这些入口操作状态，不再通过整个 CLI 随意读写对应私有状态。计划实现归拢到独立包。

负责子任务：../11-27-cli-planning-boundaries/；依赖 R1 合并。

### R3：每会话状态与有效配置来源一致

一次应用会话中的 CLI、计划协调、模型调用、工具选择和工具执行使用同一份有效配置及计划状态。不同应用会话互不修改彼此的计划和工具可见性；保留用户工具独立运行所需的环境桥接。

负责子任务：../11-27-session-state-boundaries/；依赖 R1、R2 合并。

### R4：行为和扩展兼容

- 保留命令拼写、别名、大小写规则、参数语义、未知命令处理及用户可见文本。
- 保留交互/非交互模式、stdout/stderr、JSON/NDJSON 结构和顺序、退出码及工具确认优先级。
- 保留配置键、默认值、配置文件与环境优先级、命令行覆盖及会话内模型/角色切换。
- 保留 provider 工厂、可选依赖懒加载、内置工具和用户同名覆盖、MCP 及独立工具执行签名。
- 保留会话、计划、检查点和恢复数据格式；已有数据无需迁移。
- 保留线程生成、取消、确认双向通信、Ctrl+O、撤销和检查点的实际副作用边界。

## Feature examples

这些示例冻结已有行为，不增加新功能。终端提示符是示意，不属于 stdout。

### E1：非交互文本输出

在隔离 HOME 中使用固定回复 pong 的假 provider，禁用工具、用量提示及流式输出：

~~~text
$ ai -p "ping"
pong
~~~

stdout 精确为 pong 加一个换行，退出码 0；不得出现欢迎语、Assistant 标签或 Rich 控制字符。错误和诊断仍走 stderr。TTY 与非 TTY 的差异依现有测试保持。

### E2：检查点限制及命令参数

临时交互会话尚未保存时输入：

~~~text
> /rewind
Save this chat with /save before using checkpoints.
~~~

错误走现有 stderr 路径，不要求确认、不修改文件或会话。/fork 的标题保留大小写和空格；/modelx 等未注册输入继续作为普通提示词处理。具体命令分发与文案以当前命令测试为兼容基线。

### E3：机器输出与保存数据

ai -p --json "ping" 的 stdout 仍只有一个 JSON 对象；保留现有 content、tool_calls、usage、finish_reason、model、provider、error、exit_code 等实际字段，计划请求才附加既有计划字段。stream-json 保持既有逐行事件及结束顺序；不自行简化成较早文档中的字段集合。旧会话重新打开后，检查点身份和文件回退行为保持一致。

## Out of scope

- 新增功能、配置项、CLI 参数、命令、provider 或用户迁移步骤。
- 自动代码自检、强制开发工作流、事件总线、插件框架、通用依赖注入容器或新的运行时依赖。
- 重写 provider、改名 functions/buildin/、重命名所有根目录模块、全面移除全局对象。
- 修改计划/检查点格式、改变权限决策、接受旧 bug 修复作为顺手改动。
- 以行数、文件数量或覆盖率百分比作为重构完成条件。

## Acceptance criteria

| ID | 要求 | 验收 |
| --- | --- | --- |
| A1 | R1 | 改一条命令定义即可同步分发、帮助和补全；工具公开入口、schema、参数修复、结果语义及副作用一致 |
| A2 | R2 | 会话操作、计划协调、机器输出可通过明确依赖独立测试；对应命令不再读写 CLI 私有字段；计划包不依赖 CLI |
| A3 | R3 | 两个不同配置/计划状态的应用实例交替声明并执行工具，互不改变对方的配置、计划及可见工具；不需要全局计划重置才能通过该测试 |
| A4 | R4 | 原有行为测试及针对边界新增的回归测试通过；现有保存数据可直接读取，文件恢复字节一致 |
| A5 | R4 | 各阶段完整 pytest、Ruff、相关格式检查通过；最终 strict docs、构建与既有启动性能门禁通过 |
| A6 | 全部 | 每阶段独立 PR、说明职责变化、测试证据和回退边界；父任务汇总三个子任务的验收证据及最终调用链 |

## Decisions and constraints

- 三阶段顺序执行，各自以最新 master 为基线；后续子任务必须在前置 PR 合并后重新核对证据和设计。
- 首批重构保留兼容入口，后续逐步将产品内部调用迁移到明确服务；不为保留所有旧 mock 路径制造新全局变量。
- 新测试针对行为、隔离及真实数据流，不只断言转发函数被调用。
- 更新方案已有实施授权；依据 research/test-safety-review.md 补齐测试门禁，实际启动第一子任务，父任务仅维护规划与集成验收，后两阶段保持 planning。
- 风险主要是导入顺序、懒加载、确认生成器、工作线程与检查点锁的边界，以及配置桥接。分阶段验证方式见 design.md、implement.md。
